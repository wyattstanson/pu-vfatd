Computer Networks Case Study, 2026

1. Problem

Telecom operators run virtual firewalls (vFWs) in cloud-edge networks to inspect customer traffic. Every orchestration interval (5 minutes), the operator must decide three things: how many firewall instances to run at each site, where to place them, and how to split traffic among sites.

The base paper (vFATD, Kopec-Persinski and Beben 2026) solves this as a mixed-integer linear program (MILP). It has three weaknesses that matter in practice:

  1. It plans on already-observed traffic. A flash crowd that starts between decisions hits firewalls sized for old load.
  2. It assumes every instance inspects exactly 50 Gbps. In practice this drops when IPS, DPI or IPsec are active, and depends on traffic mix.
  3. It ignores link capacities and latency budgets, so it can route traffic over full links or to distant sites.

Our system, PU-vFATD (Proactive and Uncertainty-aware), fixes these three problems with a seven-stage orchestration pipeline.

2. Seven-Stage Pipeline

2.1 Stage 1: Capacity Estimation (Eqs. 1-3)

Instead of assuming 50 Gbps, we estimate the actual inspection capacity per instance at each site. A model-based prior (Eq. 1) uses the traffic mix and known per-class inspection cost. A measurement-based estimate scales observed throughput to the maximum allowed CPU utilisation. These are blended with exponential smoothing (Eq. 3) so noisy readings do not jerk the estimate around. If telemetry is stale or missing, we use the lower of the old estimate and the prior.

Ablation impact: replacing this with fixed 50 Gbps drops served traffic from 99.84% to 96.47%. This is the single biggest factor in the system.

2.2 Stage 2: Forecasting (Eq. 4)

Instead of planning on the traffic just observed, we forecast the next interval. The forecaster is a seasonal-ratio model: it multiplies the last observation by the ratio between yesterday-at-this-time and yesterday-one-interval-earlier, with a 3-interval moving window. It outputs both a mean and a standard deviation (the spread of its past errors).

Eq. 4 -- Forecast mean and spread

We use a statistical forecaster (3.5% MAPE), not the neural model described in the methodology document (Eq. 5). The reserve mechanism in Stage 3 covers the remaining error.

2.3 Stage 3: Uncertainty-Aware Reserve (Eqs. 6-8)

A fixed safety margin does not work well: it wastes capacity when traffic is steady and is too small during a surge. Instead, we set the reserve from the forecast's own uncertainty. The planning demand (Eq. 8) is the core of the proactive approach.

Eq. 6 -- Normalised forecast error
ei,kt−1=di,kt−1−μi,kt−1σi,kt−1
Eq. 8 -- Planning demand
D^i,kt=max(μi,kt+max(qit,0)σi,kt, di,kt−1)

The multiplier q increases after an under-forecast and decreases slowly otherwise, tracking a 5% miss rate target. The outer max ensures we never plan for less than the last measurement, so capacity is not released during an ongoing surge. Reserve coverage (PICP) is 94.6%, close to the 95% target.

Given the planning demand, we minimise a cost function (Eq. 9) with six terms: deployment, transport, loss penalty, latency, reconfiguration, and migration costs. The decision variables are the number of instances at each site and the traffic split fractions.

2.5 Stage 5: Controller (Eqs. 23-36)

The methodology document describes a PPO (Proximal Policy Optimisation) controller trained as a constrained Markov decision process. We did not implement this. The controller slot is filled by: PU-vFATD uses the MILP solver from Stage 4 (mean solve time ~109 ms); PU-vFATD-fast uses a greedy proposer (~1.2 ms). Both are checked by the SafetyGate. The proposer interface is modular -- a trained PPO policy would be a drop-in replacement.

2.6 Stage 6: SafetyGate (Algorithm 1, Eqs. 37-39)

Every proposed configuration is checked before it reaches the network. The fallback hierarchy: (1) accept if already feasible, (2) greedy repair of overloaded sites and links, (3) projection to the closest feasible configuration, (4) revalidate the running configuration against current demand, (5) solve the full MILP under a time limit, (6) emergency mode: maximum instances, protected classes first, alarm raised.

Eq. 37 -- Feasibility test
𝐚t∈𝒜t⟺Ωj(𝐚t)=0,∀j∈{cap,link,lat,cov}

Traffic is never forwarded without inspection. If there is not enough capacity, traffic is blocked. This is a structural invariant enforced in the simulator and verified by unit tests.

2.7 Stage 7: Execution (Eq. 39)

Make-before-break deployment: start new instances first, wait for readiness, install new routing rules, then drain old instances. Sending a command is not taken as success -- the controller records what the execution unit actually confirms.

4. Results (Realistic Constraints)

Each experiment runs 288 intervals (one simulated day) on a 4-PoP, 7-site network (4 edge sites with 3 slots, 2 regional with 8, 1 cloud with 24) with six stress scenarios. Three seeds per combination; means reported.

PU-vFATD achieves 99.84% served-traffic ratio at the lowest cost. The adapted vFATD-MILP scores 94.64% because it still uses fixed 50 Gbps capacity and reactive planning. Under the base paper's original assumptions (no link limits, unlimited capacity), all methods are close -- the vFATD MILP is about 3% cheaper. Our method is better specifically because the realistic constraints matter.

6. Contributions vs. Base Paper

  1. Proactive planning (Eqs. 4, 7, 8): forecast + adaptive reserve instead of reactive.
  2. Variable capacity estimation (Eqs. 1-3): measured per-site capacity instead of fixed 50 Gbps.
  3. Extended constraints (Eqs. 19-20): link capacity and latency budgets.
  4. SafetyGate (Algorithm 1, Eqs. 37-39): multi-level fallback guaranteeing feasibility.
